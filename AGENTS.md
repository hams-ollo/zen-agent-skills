# AGENTS.md: rules for the Zen Starter Kit repository

Canonical rules for every AI agent working in this repository (Claude Code, Cursor, Codex, OpenCode, and any tool that reads `AGENTS.md`). This is the single source of truth. Any `CLAUDE.md`, `.cursor/rules/*.mdc`, or `.github/copilot-instructions.md` in this repo is a thin pointer back here.

This repo is the **Zen Solutions Starter Kit**: a portable, cross-harness library of agent skills, plus the tooling to install them into any project and any AI coding tool. It dogfoods its own system.

---

## 0. What this repository is

A skills library, not an application. The deliverables are the skills under [`.agents/skills/`](.agents/skills/) and the tooling under [`scripts/`](scripts/) that distributes them. Success is measured by whether a skill is portable (works across harnesses), self-contained (needs no hidden context), and genuinely used.

## 1. Layout

| Path | Holds |
|---|---|
| [`.agents/skills/`](.agents/skills/) | The skills. One directory per skill, each with a `SKILL.md` as its harness-agnostic body. |
| [`.agents/rules/house-style.md`](.agents/rules/house-style.md) | The swappable writing/formatting conventions the skills assume. Adopters may replace it. |
| [`.agents/hooks/`](.agents/hooks/) | Optional runtime guardrails (Python on stdin). Empty until a rule earns enforcement. |
| [`scripts/`](scripts/) | `install.py` (cross-platform installer), `build-adapters.py` (per-harness wrappers), `validate-skills.py` (kit-level lint). |
| [`docs/CATALOG.md`](docs/CATALOG.md) | The tiered skill catalog and roadmap. |

## 2. How a skill is structured

Each skill is a directory under `.agents/skills/<name>/` containing:

- **`SKILL.md`** (required): YAML frontmatter (`name`, `description`) then a Markdown body. The body is the **single harness-agnostic source of truth**. It must not depend on any one tool's features.
- **`templates/`**, **`references/`**, scripts (optional): supporting files, referenced from `SKILL.md` one level deep.

The `description` frontmatter says both **what** the skill does and **when** to use it, and should be a little pushy: agents tend to under-trigger skills. Keep `SKILL.md` focused (aim under ~500 lines); push detail into referenced files.

## 3. Portability contract (the whole point)

- **`AGENTS.md` is canonical** in any repo this kit scaffolds. Cursor, Codex, and OpenCode read it natively; a thin `CLAUDE.md` pointer covers Claude Code.
- **Write once, adapt thin.** A skill's logic lives only in its `SKILL.md`. Any per-harness file (a Cursor `.mdc`, a slash-command wrapper) is generated by [`scripts/build-adapters.py`](scripts/build-adapters.py), never hand-maintained in parallel.
- **No tool lock-in in skill bodies.** If a skill needs a capability only one harness has, gate it behind a clearly labeled optional section, do not assume it.

## 4. Conventions

Follow [`.agents/rules/house-style.md`](.agents/rules/house-style.md) for writing and formatting. In brief: no em-dashes, sentence-case headings, named sources, relative markdown links, Mermaid for diagrams. That file is swappable; this reference to it is not.

- **Python** (tooling under `scripts/`): standard library only where possible, so the installer runs anywhere with a bare Python 3. PEP 8. No third-party dependency unless it is truly load-bearing and documented.
- **Cross-platform**: the tooling targets Windows, macOS, and Linux. Prefer `pathlib` and `os.path` over shelling out; never assume POSIX symlinks are available.

## 5. Contribution bar

A skill earns a place in this kit only if it is something the author actually uses and has iterated on. Do not add speculative skills. Hyper-specific personal skills stay out of the shared kit (see `docs/CATALOG.md` tiers). When in doubt, a skill belongs in the catalog as "planned," not in `.agents/skills/` as shipped.
